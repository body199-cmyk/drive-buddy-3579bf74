# ADR-0003 — Dedupe source_key ينتقل إلى هوية MTProto الثنائية

- الحالة: مقبول (2026-08-23)
- المرجع: تدقيق خارجي 2026-08-23 نتيجة C-03 · دستور §11 و§15
- قرار مرتبط: KNOWN_ISSUES #69/#70 غير متأثرين

## السياق

`source_key()` كانت تبني المفتاح `tg:{chat_id}:{message_id}:{file_unique_id}`.
الدستور §11 يحظر استخدام `file_unique_id` للدedupe صراحة، و§15 يعتمد هوية
رسالة MTProto المستقرة `(marked chat_id, message_id)`. المفتاح الرباعي خالف
الحظر وجعل اسم الحقل يوحي بعقد Bot API بينما المنتج Telethon User-account فقط.

## القرار

المفتاح الجديد: `tg:{int(chat_id)}:{int(message_id)}` — بدون أي مكوّن ملفي.

`file_unique_id` يبقى حقل metadata في SQLite للعرض/التشخيص فقط، ولا يدخل في
أي حساب هوية أو مطابقة تكرار، الآن أو لاحقًا (لا مسار توافق دائم عبره).

## مصير مفاتيح appProperties الرباعية القديمة على Drive

1. لا backfill: أي إعادة كتابة خصائص على أصل منشور تتطلب تحقق metadata كامل
   لكل ملف، وتعقيد غير متناسب مع حجم الاستخدام الحقيقي الحالي.
2. القرار المعتمد: **قبول إعادة فحص لمرة واحدة**. أول نقل بعد الترقية لن يتعرف
   على نسخ Drive القديمة ذات المفاتيح الرباعية كمكررات وقد يرفع نسخة جديدة
   بمفتاح ثنائي. النسخ القديمة تبقى كما هي ولا تُحذف (§11: تنظيف غير أعمى).
3. الأصول الجديدة كلها تُكتب بالمفتاح الثنائي، فتضاؤل المشكلة ذاتيًا مع الوقت.

## الآثار

- `duplicate_detector` و`drive_client` يعملان دون تغيير لأنهما يستهلكان
  قيمة `source_key` كما هي.
- اختبار تنفيذي جديد يثبت: نفس الرسالة بdocument IDs مختلفة ⇒ نفس المفتاح،
  ورسالتان مختلفتان ⇒ مفتاحان مختلفان.
