## 1. Goal and expected workflow

TeleDrive / Drive Buddy is a web dashboard whose transfer engine runs inside Google Colab and uses Google Drive as storage. The experimental architecture is:
- Vercel hosts the web UI and the experimental Preview deployment.
- The Google Colab notebook starts the existing Python transfer engine and FastAPI dashboard. The current design uses port 8765 and existing Gradio fallback behavior where applicable.
- Cloudflare Quick Tunnel exposes the temporary Colab dashboard through a temporary *.trycloudflare.com URL.
- The notebook creates a short-lived, single-use handoff token. The user opens a Vercel Preview /connect link generated by the notebook. The browser exchanges the handoff token for the active runtime bearer token, then connects to the remote dashboard.
- Google Drive is the destination using the notebook's existing Drive integration and user's Colab authorization.

- FastAPI dashboard backend and authentication/CORS middleware.

- Same-origin bypass was restricted to requests where Host ends with .googleusercontent.com, .colab.google, or .prod.colab.dev AND Sec-Fetch-Site equals same-origin. This is intended to prevent the public tunnel from inheriting a Colab-proxy bypass.
- Security is not yet proven. Confirm actual Host/origin/Fetch-Metadata headers in the real Colab proxy and Cloudflare tunnel. Host and Sec-Fetch-Site are headers, not a complete security boundary against arbitrary clients. Test real CORS preflights and bearer auth.

### src/components/teleDrive/remoteColabBridge.ts
- Browser-side bridge for the remote Colab dashboard.
- Supports *.trycloudflare.com runtime hosts.
- Fetch credentials mode is omit for .trycloudflare.com and include for the Colab proxy case.
- Review URL scheme and hostname validation before supporting any additional hosts.

### src/routes/connect.tsx
- Parses URL fragment format #url=<tunnel-url>&handoff=<one-time-token>.
- Attempts to clear the fragment from the visible address bar with history.replaceState.
- Validates the target host using RemoteColabBridge with a dummy token before exchanging credentials.
- POSTs to /api/pairing/exchange with JSON {handoff_token}, credentials omit, and cache no-store.
- Checks response.ok and JSON Content-Type, validates {ok:true, token:string}, then creates the real bridge with the returned runtime token.
- Uses a ref to avoid handling the same handoff twice under React StrictMode.
- Must be tested in a real browser. Clearing the fragment is a mitigation, not a guarantee that secrets cannot be captured by extensions, screenshots, copied links, logs, or telemetry.

## 5. Handoff token security design

Intended lifecycle:
- The active runtime bearer token is a password for the current live runtime.
- Notebook creates a separate random handoff token using secrets.token_urlsafe(32).
- It is stored in runtime memory in ctx.remote_handoff_tokens with a five-minute expiry.
- Generated link includes tunnel URL and short-lived handoff token, not the active runtime token.
- Browser exchanges token via POST /api/pairing/exchange.
- Backend consumes/pops the handoff token and validates expiry and active runtime token availability; successful exchange is intended to be single-use.
- Exchange response should include no-store headers; browser fetch uses cache no-store.
- Notebook output must not print the active runtime token or reusable token-bearing API URL.

Residual risks:
- Someone who obtains a valid handoff URL before expiry may redeem it first. Never post it publicly; retain short expiry and one-use behavior.
- Confirm concurrent redemption cannot redeem the same token twice; consumption should be atomic under the runtime's execution model.
- Ensure logs never print handoff or runtime tokens.
- Confirm runtime token is not stored in localStorage, sessionStorage, query parameters, or persistent logs.
- Ensure UI errors never reveal bearer tokens.
- Every endpoint that reads/writes files, controls jobs, or exposes private state must require bearer authentication.
- CORS is not authentication. Sensitive server operations need their own auth checks.
- Review public tunnel exposure and privacy before connecting an important Drive account.

## 9. Troubleshooting

### Vercel READY but app won't connect
READY is deployment state only. Check whether Preview URL is current; Colab runtime is active; Cell 4 completed; dashboard listens on expected port; Cell 5 printed a valid tunnel URL; handoff has not expired; and the browser error is not deployment protection/SSO, CORS, 401, or a non-JSON response.

### Handoff unauthorized or fails
Run notebook cells in order and use a freshly generated link. Do not reuse old links: token is one-use and expires after five minutes. Confirm runtime token is present and has not rotated. Inspect redacted response status/logs. Never paste live tokens into chat or GitHub. Verify real Host and Sec-Fetch-Site headers before changing same-origin rules.

### Tunnel fails to start
Confirm Linux amd64 architecture or safely select the correct asset for actual architecture; check download and hash; verify dashboard port locally; inspect cloudflared output/exit code; confirm old process was stopped. Do not disable checksum verification to work around a failure.

### Transfer fails
Separate tunnel connectivity from the transfer engine. Check queue state, engine logs, Drive authentication and permissions, destination path, and storage. Test with a disposable small file and verify size/hash before claiming success.
