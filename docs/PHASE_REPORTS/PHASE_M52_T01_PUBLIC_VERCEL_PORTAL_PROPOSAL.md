# M52-T01 — مقترح بوابة TeleDrive العامة عبر Vercel (خطة مستقبلية فقط)

**التاريخ:** 2026-10-21  
**الحالة:** PLANNED — NOT IMPLEMENTED  
**قرار المالك:** حفظ الفكرة بالتفاصيل في خطة العمل المستقبلية، وعدم البدء في تنفيذها الآن.

## 1. المشكلة والهدف

تجربة الاستخدام الحالية تتطلب من المستخدم العادي الوصول إلى المستودع أو رابط Google Colab، وتشغيل الخلايا، وربط Google Drive وإعداد Telegram أو غيره يدويًا حسب الوظائف التي يريدها. هذا عبء تقني غير مناسب لخدمة عامة سهلة الاستخدام.

الهدف المستقبلي هو رابط واحد لموقع TeleDrive عام — يمكن استضافته مبدئيًا على Vercel — يسمح للمستخدم بتسجيل الدخول وربط حساباته وإدارة التنزيلات من لوحة تحكم واحدة، دون الحاجة إلى فهم GitHub أو التعامل المباشر مع Notebook بعد الإعداد قدر الإمكان.

هذه وثيقة تصور وليست التزامًا بأن التشغيل التلقائي الكامل أو الخدمة المجانية الدائمة ممكنان دون قيود.

## 2. تجربة المستخدم المطلوبة

1. يفتح المستخدم رابط الموقع العام من الهاتف أو الكمبيوتر.
2. يسجل الدخول بطريقة آمنة، ويفضل Google OAuth مع فصل هوية الدخول عن صلاحيات Drive.
3. يختار «ربط Google Drive» ويوافق على أقل نطاقات OAuth لازمة للوظائف التي يستخدمها.
4. يختار ربط Telegram عند الحاجة فقط، مع توضيح نوع الاتصال المطلوب (حساب مستخدم/جلسة أو Bot Token) وعدم طلب بيانات غير ضرورية.
5. يرى صفحة حالة واضحة: Drive connected/disconnected، Telegram connected/disconnected، محرك TeleDrive online/offline، آخر اتصال، ورسالة خطأ مفهومة.
6. يتحكم في المحرك الحقيقي من لوحة واحدة: بدء/إيقاف/استكمال المهام، طابور التنزيل والنقل، التقدم والسرعة، الملفات والوجهة، وسجل أخطاء آمن.
7. عند انقطاع Colab أو انتهاء جلسته، تظهر حالة صريحة وخيار إعادة الاتصال/بدء الجلسة بدل عرض حالة وهمية أو نجاح غير مؤكد.

المبدأ: لا بيانات تجريبية في لوحة التحكم؛ كل حالة وأمر يجب أن يعكس نتيجة حقيقية من المحرك.

## 3. المعمارية المقترحة — على مراحل

### المرحلة A: بوابة واجهة وحسابات

- استخدام Vercel لاستضافة واجهة ويب سريعة ومتجاوبة، وصفحات تسجيل الدخول والإعدادات، وواجهات API قصيرة مناسبة لطبيعة Vercel.
- قاعدة بيانات مناسبة لتخزين حسابات المستخدمين ومعرّفات الجلسات وحالة الاتصال وإعدادات غير سرية. اختيار مزودها لاحقًا بعد تقدير التكلفة ومتطلبات الخصوصية.
- لا يُخزّن في الواجهة أو المتصفح أي Google refresh token أو Telegram session أو Bot Token أو مفتاح داخلي للمحرك.
- تخزين الأسرار على خادم موثوق ومشفرة/محكومة بالصلاحيات، مع فصل بيانات كل مستخدم واختبارات تمنع الوصول المتبادل.

### المرحلة B: تكامل Google Drive

- Google OAuth للتفويض إلى Drive، مع طلب أقل الصلاحيات اللازمة واستخدام مسار واضح لسحب الإذن/فصل الحساب.
- التمييز بين «تسجيل الدخول عبر Google» و«منح صلاحية Drive»؛ فهما ليسا خطوة واحدة بالضرورة.
- حفظ التوكنات في backend آمن فقط، مع التعامل الصحيح مع انتهاء الصلاحية والتجديد والإلغاء.
- عدم تخزين ملفات المستخدم أو نسخها على Vercel لمجرد تمريرها؛ يبقى النقل عبر المحرك/مسار التخزين المناسب.

### المرحلة C: تكامل Telegram

- واجهة إعداد اختيارية تشرح هل المستخدم يحتاج جلسة Telegram user أم Bot Token، بناءً على وظيفة Telegram الحالية في TeleDrive.
- لا تعرض أسرار الجلسة أو الرموز في React أو السجلات أو ملفات Git أو تقارير التشخيص.
- لا تُفترض إمكانية استخدام Bot API بدل جلسة المستخدم؛ يجب فحص الوظائف الحالية ومتطلبات Telegram قبل اختيار البروتوكول.
- الحفاظ على Vault وآلية الاستعادة الحالية وعدم تغييرهما ضمن مرحلة التخطيط هذه.

### المرحلة D: اتصال آمن بمحرك TeleDrive الحالي

- في النسخة الانتقالية يمكن أن يبقى محرك التنزيل على Google Colab، بينما تتولى Vercel الواجهة وتنسيق الاتصال.
- يلزم بروتوكول backend-to-worker موثق ومصادق عليه، مع هوية منفصلة لكل مستخدم، صلاحية محدودة، انتهاء/تدوير بيانات الاتصال، ومقاومة إعادة إرسال الأوامر.
- اتصال صادر من العامل (worker) إلى خدمة الربط قد يكون أسهل من محاولة فتح منفذ عام داخل Colab، لكن يجب تقييم قيود الشبكة ومدة الجلسة قبل اعتماده.
- Heartbeat/lease لعرض online/offline، وإعادة اتصال آمنة، وحماية من الجلسات القديمة، وتزامن الطابور.
- واجهة المستخدم لا تعتبر الأمر ناجحًا إلا بعد رد مؤكد من المحرك، وتعرض حالات pending/running/failed بوضوح.
- لا نعيد كتابة محرك التنزيل الحالي لمجرد إضافة بوابة ويب؛ ندرس واجهات المحرك الحالية ونضيف طبقة تكامل بأقل تغيير ممكن.

### المرحلة E: قرار تشغيل Colab أم worker دائم

**الخيار 1 — Vercel + Colab (مرحلة انتقالية منخفضة التكلفة):**
- الاستفادة من المحرك الحالي وتقليل إعادة البناء.
- قد يحتاج المستخدم إلى تشغيل Colab مرة أولى أو إعادة تشغيله بعد انتهاء الجلسة، ما لم تثبت وسيلة موثوقة ومسموح بها للأتمتة.
- لا يجوز ضمان أن Colab المجاني سيبدأ تلقائيًا دائمًا أو سيبقى متصلًا أو يوفّر الموارد؛ حصص الجلسات والتوافر قد تتغير.

**الخيار 2 — Vercel + worker/خادم منفصل (اتجاه أكثر استقرارًا):**
- تشغيل المحرك على خدمة مصممة للعمليات المستمرة بدل الاعتماد على جلسة Notebook مؤقتة.
- يحتاج إلى تقدير تكلفة التخزين، المعالج، الشبكة، مدة التشغيل، ونقل البيانات؛ قد لا يكون مجانيًا.
- يلزم فصل الملفات وعمليات المستخدمين، حدود موارد/سرعة، إيقاف المهام عند تجاوز الحصة، وتنظيف الموارد بطريقة آمنة.

**الخيار 3 — أتمتة تشغيل Colab بالكامل:**
- لا يعتمد عليه كأساس قبل اختبار عملي وإثبات أنه موثوق ومتوافق مع سياسات Google.
- لا تفترض Vercel القدرة على تشغيل جلسة Colab مباشرة بمجرد فتح الموقع؛ Vercel ليس بيئة worker طويلة العمر.

التوصية الأولية: صمم الواجهة والـAPI بحيث يمكن أن يتغير worker لاحقًا، وابدأ بتقييم Vercel + Colab كمرحلة انتقالية فقط. لا تتخذ قرار الاستضافة النهائي قبل نموذج تكلفة وتجربة إثبات مفهوم.

## 4. متطلبات الأمان والخصوصية

- فصل صارم بين مستخدمي الخدمة: ملكية كل مهمة وطابور ووجهة تخزين وتوكنات مرتبطة بمعرّف المستخدم.
- منع وضع OAuth secrets وTelegram credentials وworker secrets في frontend أو query strings أو سجلات الأخطاء.
- تشفير الأسرار أثناء التخزين والنقل، وصلاحيات دنيا، وإلغاء الجلسات، وتدوير المفاتيح، ومراجعة السجلات.
- حماية API من CSRF/إساءة الاستخدام، تحديد المعدل والحصص، التحقق من الملكية لكل طلب، ومنع الوصول إلى روابط/ملفات مستخدم آخر.
- عدم استخدام رابط worker عام غير محمي؛ كل أمر يجب أن يكون مصادقًا ومحدد النطاق.
- تصميم سياسة احتفاظ وحذف بيانات واضحة، مع عدم حذف بيانات Drive أو Telegram Vault تلقائيًا بسبب فشل الاتصال.
- تحديد ما إذا كانت الخدمة للاستخدام الشخصي أو عامة متعددة المستخدمين قبل تصميم قاعدة البيانات ونموذج الصلاحيات.

## 5. نطاق لوحة التحكم

- حالة المحرك والاتصال الفعلية.
- طابور التنزيل/الرفع/النقل مع حالات واضحة.
- سرعة وتقدم ووقت تقديري عند توفر بيانات حقيقية فقط.
- إيقاف/استكمال/إلغاء آمن وفق قدرات المحرك الحالية.
- ربط/فصل Drive وTelegram، إعدادات المستخدم، وجهة التخزين.
- رسائل خطأ قابلة للفهم مع معرف تشخيص غير حساس.
- تحديثات مباشرة عبر polling محدود أو قناة مناسبة بعد تقييم Vercel والـworker؛ لا تعتمد على اتصالات طويلة لا تتناسب مع حدود الاستضافة.

1. **Discovery / audit:** قراءة `docs/AI_HANDOFF.md` و`docs/TODO.md` والكود الحالي، ورسم تدفق المصادقة والطابور وواجهات المحرك؛ تحديد ما يمكن إعادة استخدامه.
2. **Architecture decision record:** مقارنة Colab worker مع worker دائم، تكاليف شهرية/حدود مجانية، متطلبات المستخدم الواحد مقابل multi-user.
3. **Proof of concept:** مستخدم واحد فقط، OAuth/Drive، worker واحد، حالة اتصال حقيقية، وأمر اختبار محدود؛ لا نقل بيانات حقيقية قبل مراجعة الأمان.
4. **Security review:** نموذج تهديد واختبارات لعزل المستخدمين وتسرب الأسرار وانتهاء الجلسات وإعادة الاتصال.

6. **Live acceptance:** تجربة من جهاز Android ومن متصفح عادي، ثم اختبار انقطاع/إعادة اتصال وعمليات Drive/Telegram فعلية بحساب مخوّل.
7. **Public beta:** تفعيل الاستخدام العام بعد مراقبة التكاليف والحدود والإبلاغ عن الأخطاء وسياسة الخصوصية.

## 7. معايير القبول

- المستخدم يصل من رابط واحد ولا يحتاج لتصفح GitHub.
- حساب Drive لكل مستخدم معزول ولا يرى مستخدم ملفات أو مهام غيره.
- Telegram اختياري ويعمل وفق طريقة الربط المدعومة فعلًا.
- كل عناصر التحكم تتصل بالمحرك الحقيقي؛ لا بيانات وهمية ولا رسائل نجاح مسبقة.
- انقطاع worker يظهر بوضوح ولا يفسد الطابور أو بيانات المستخدم.
- الأسرار غير موجودة في الواجهة أو Git أو logs.
- تكلفة التشغيل وحدود الاستخدام واضحة قبل إتاحة الخدمة العامة.
- الاختبارات الآلية والاختبارات الحية موثقة كلٌّ على حدة.

## 8. ما لا ينبغي فعله

- لا تبدأ التنفيذ ضمن إصلاحات TeleDrive الجارية ما لم يطلب المالك بدء هذا المشروع صراحة.
- لا تعِد بناء المحرك أو تغيّر Telegram Vault أو قاعدة البيانات الحالية دون حاجة مثبتة.
- لا تعتبر نجاح CI دليلًا على أن OAuth أو Colab أو Drive أو Telegram يعمل حيًا.
- لا تعد المستخدمين بتشغيل مجاني مستمر أو تشغيل Colab تلقائي مضمون.
- لا تجعل نشر واجهة Vercel يعني تلقائيًا أن محرك التنزيل يعمل؛ يجب إظهار صحة worker الحقيقية.
- لا تُدمج أي تغييرات أو تنشئ حسابات/خدمات خارجية أو تنشر واجهة عامة قبل الموافقة على خطة التنفيذ والأمان والتكلفة.
