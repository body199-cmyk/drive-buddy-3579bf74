# AI_RULES — قواعد تشغيل الذكاء الاصطناعي (TeleDrive)

> المرجع الأعلى: `docs/CONSTITUTION.md` (v5.0.0). هذه القواعد تشرح السلوك فقط ولا تضعف أي بند دستوري.
> **إصدار المنتج: 4.5.0 · إصدار الحوكمة: 5.0.0.** كل إحالات الأقسام هنا بترقيم v5.0.

## 1) الأدوار الثلاثة (لا تداخل)

| الدور | من | ماذا يفعل | ما لا يفعله |
|---|---|---|---|
| **Brain — المهندس والمراجع** | Brain عبر ClickUp Docs | يفحص GitHub والدستور، يصمم المعمارية، يكتب الخطة والكود الكامل داخل DOC، يحدد الملفات والأوامر والاختبارات، ويراجع النتيجة بعد كل تنفيذ | لا يعدّل GitHub ولا يدّعي ذلك |
| **LM Arena Agent — المنفّذ الوحيد** | LM Arena | يقرأ الريبو والدستور وDOC، يفحص baseline، ينشئ branch، يطبّق، يشغّل التحقق، يحدّث الذاكرة، commit وpush أو PR، ويبلّغ بالنتائج الفعلية | لا يعيد تصميم المعمارية، لا يخفي فشلًا، لا يدّعي push بلا SHA |
| **Owner — المالك** | body199-cmyk | يحدد الأولويات، يعتمد ADR وتغييرات الدستور، يرسل روابط DOC، يوفر الاعتماد داخل Colab فقط، ويجري الاختبار الحي، وينفّذ ما يعجز عنه المنفّذ لقيود المنصة | — |

**Lovable خرج من المشروع نهائيًا (§3).** لا يُذكر كمنفّذ ولا يُطلب منه شيء، وأي إشارة قديمة إليه تُصحَّح إلى LM Arena Agent. ملاحظة تقنية: المستودع لا يزال متصلًا بـLovable كمرآة مزامنة (`AGENTS.md`)، ولهذا يبقى منع إعادة كتابة التاريخ ساريًا؛ المزامنة ليست تفويضًا تنفيذيًا.

## 2) قواعد الأدلة (لا استثناء)

- كل ادعاء "موجود/شغال/ناجح" يستند إلى: ملف في الشجرة الحالية + SHA + مخرجات أمر فعلي. الرد النصي وحده ليس دليلًا.
- مفردات الحالة إلزامية وليست تجميلية: `Implemented` / `Fake-tested` / `Code-complete candidate` / `Colab-ready` / `Complete` (التعريفات في §17).
- أي ادعاء عن تحقق حقيقي (Telegram أو Drive أو نقل ملف) ممنوع قبل المرحلة 10 الموثقة في `docs/PHASE_REPORTS/PHASE_10.md`.
- عند تعارض مصدرين: سجّل التعارض وتوقف — لا تدمج صامتًا (§2، §20).
- `compileall` و`launcher --check` ليسا بديلًا عن `pytest` (§9.7). والاختبارات الوهمية ليست دليل تكامل حقيقي.
- **نجاح محلي ليس نجاح CI.** لا تقل "البوابات خضراء" إلا بمعرّف تشغيل GitHub Actions ناجح.

## 3) قواعد التعديل

- بند واحد من `TODO.md` لكل جلسة، بـTASK ID، أصغر تغيير آمن، commit واحد واضح الرسالة يبدأ بالـTASK ID.
- الأصول المحمية لا تُلمس إلا بموافقة مالك صريحة + سبب + خطة تراجع: الدستور، الاعتماديات المثبَّتة، النوت‌بوك ومولده، تاريخ Git المنشور، والأرشيف التاريخي.
- أي تغيير في `requirements.lock` أو `bun.lock` يحتاج دليل توافق + موافقة (§11).
- لا force-push ولا rebase ولا amend لأي commit منشور (§10).
- قبل كل push: بوابات §16 محليًا + فحص أسرار ناجح (§11).
- لا تلمس `main` مباشرة. فرع جانبي + PR دائمًا.

## 4) قواعد التقارير

- كل رد تنفيذ يلتزم صيغة **§18**. جلسة الاستئناف تلتزم إضافةً بصيغة **§9.9**.
- كل مرحلة تكتب تقريرها في `docs/PHASE_REPORTS/` — التقارير لا تُعدَّل بعد الدفع ولا تمحو فشلًا سابقًا (§7).
- عند الانتهاء: تحديث إلزامي لـ`AI_HANDOFF.md` + `ACTIVE_TASK.md` + `TODO.md` + `CHANGELOG.md` + `KNOWN_ISSUES.md`.
- ما لم يُشغَّل يُذكر صراحة تحت `TESTS NOT RUN OR NOT PROVEN`. الحقل الفارغ مرفوض.

## 5) شروط التوقف (STOP CONDITIONS)

توقف فورًا وأبلغ المالك عند: اختلاف المستودع القانوني، اختلاف HEAD بلا تفسير، تعارض مصادر، ملف مفقود، اختبار فاشل، اعتماد أو صلاحية غير متاحة، فشل GitHub، ظهور سر، محاولة تطبيق ثانٍ، أو ادعاء غير قابل للإثبات. **التوقف مقبول؛ التظاهر بالنجاح مرفوض (§20).**

## 6) معاملة الأسرار

- API ID/hash، session strings، توكنات، أرقام هواتف، رموز دخول، كلمات 2FA: لا تُكتب أبدًا في ملفات الريبو ولا السجلات ولا اللقطات ولا ZIP ولا رسائل الدعم ولا DOC.
- توكن GitHub: يُستخدم في الأمر فقط، لا يُخزَّن في أي ملف، ويُنصح بمسحه بعد كل دفعة.
- كل سجل يُنقَّح قبل نشره. لا تستخدم أي توكن أو سر يظهر في المحادثة (§11).
